## 2. 启动、目录和统一入口

在 PowerShell 中运行：

```powershell
Set-Location -LiteralPath 'D:/双循环论文写作/代码项目/AFC2.0'
conda activate AFC
$env:PYTHONUTF8 = '1'
$env:PYTHONIOENCODING = 'utf-8'
$env:MKL_THREADING_LAYER = 'SEQUENTIAL'
$env:OMP_NUM_THREADS = '1'
$env:PYTHONPATH = (Join-Path (Get-Location) 'src')
python scripts/load_prediction.py protocol
python scripts/load_prediction.py web --port 8765
```

浏览器打开 [本地工作台](http://127.0.0.1:8765)。默认服务根目录是项目内 `data/paper1/service`。如需隔离一次运行，在子命令前加全局参数：

```powershell
python scripts/load_prediction.py --output-dir 'data/paper1/my_run' web --port 8765
```

网页、CLI与桌面共享 `TrainingService`。同一输出目录只允许一个 `JobService` 持有任务锁：网页正在运行时，通过其 HTTP API 提交训练，不再另开指向同目录的 CLI 训练服务。关闭浏览器不终止后台任务；停止服务会使未完成任务中断，重启后须显式重新创建任务，不自动续训。

|---|---|---|
| GET `/api/v1/protocol` | `protocol` | 当前轮次映射、折定义与特征契约 |
| POST `/api/v1/discover` | `discover request.json` | 有上限的文件发现，不放行数据 |

| POST `/api/v1/prepare-feed` | `prepare-feed request.json` | 只准备独立进给监督 |
| POST `/api/v1/prepare` | `prepare request.json` | 准备同网格进给、负载快照 |
| POST `/api/v1/preview` | `preview request.json` | 检查固定快照并预览训练 |
| POST `/api/v1/jobs` | `train request.json` | 创建持久化后台训练任务 |
| GET `/api/v1/jobs`、GET `/api/v1/jobs/<job_id>` | HTTP读取 | 查询状态和最近事件 |
| POST `/api/v1/jobs/<job_id>/cancel` | CLI训练时 Ctrl+C | 请求取消 |
| GET `/api/v1/models` | `models` | 正式冻结模型列表 |

POST 请求是 UTF-8 JSON对象，最大8 MiB。服务只绑定 `127.0.0.1`，跨来源浏览器请求被拒绝。CLI JSON文件必须为UTF-8；统一使用 `/` 表示JSON中的Windows路径，避免反斜杠转义错误。HTTP失败通常返回 `{"error":"具体原因"}`；后台任务是否成功应检查任务状态和内层业务结果。

另开 PowerShell 后可复制以下调用模式：

```powershell

```


## 3. 清单、角色与基础标签凭据

### 3.1 一条记录代表一次完整实测

清单结构为 `{"schema":"afc.dataset_manifest.1","records":[...]}`。文件路径相对于清单JSON所在目录解释；直接传内联清单时使用绝对路径。记录可以将元数据放在 `metadata` 下；建议统一使用平铺字段，避免同名字段冲突。

| 字段组 | 字段及要求 |
|---|---|
| 身份/用途 | `record_id`唯一；`status`为`active`或`superseded`；`dataset_role`见下表；`program_id`为明确程序族 |
| 原始资料 | `nc`、`measurement`、`machine`；负载还需`process` |
| 开发协议 | 仅`development`要求`round_id`为1—90整数；`combination`、`parameter_group`、`feature`、可选`program_slot`匹配`protocol`，不能用取模推断 |
| 采集顺序 | `actual_event_order`为审核后的非负整数；`acquired_at`为实际时间；补采沿实际采集顺序追加 |
| 工艺/刀具 | `process_aligned=true`、`process_version`、`diameter_mm>0`、正整数`teeth`、`tool_session`；按需提供`steady_lines` |
| 机床/程序 | `machine_id`、`machine_settings_version`、`program_version`、`machining_mode`、正数`feed_override` |
| 审核 | `complete`、`round_complete`、`alignment_reliable`、`no_alarm`、`tool_healthy`必须逐项明确通过 |
| 接触 | 已对齐工艺表提供`ap_mm/ae_mm`，或审核的`cutting_contact_confirmed`；G1/G2/G3本身不证明接触 |
| 对齐修正 | 必要时提供`measurement_line_offset`、`process_line_offset`；未知采样周期可提供已核实的`sample_period_s` |
| 工况 | `condition_descriptors`为物理描述；`condition_id`只用于追溯及显式编号诊断对照，不能用程序号/轮次代替 |

角色及用途：

| `dataset_role` | 用途 | 是否参加正式网络开发 |
|---|---|---|
| `development` | R01—R90、每轮外形/曲面/混合/斜面/台阶，共450有效位置 | 是 |
| `memory_validation` | 完整程序重复加工的独立记忆验证 | 否 |
| `target_adaptation` | 新工况拟合/校准资料 | 只用于指定适配对照 |
| `adaptation_validation` | 独立适配验证或区间外部验证 | 不参与拟合；微调时可用于早停 |
| `interval_calibration` | 独立完整记录的区间拟合 | 否 |
| `independent_test` | 冻结模型后的最终测试 | 否，不用于选参、早停或校准 |

同一NC的独立重复实测可以跨开发折；同一实测内容更名、复制或改Scope头部后仍只算一个来源。不同用途应保留完整程序隔离；服务同时检查程序族和实际NC内容。记忆验证有明确例外，不因此允许适配、校准或最终测试混入开发。

机床JSON的schema为 `afc.machine.1`。需按实际机床核实三轴速度/加速度/jerk上限、插补周期、轮廓及拐角容差、初始位置、行程范围、坐标偏置，以及NC用到的刀长、回零、等待和控制器语义。未知设置会导致几何或兼容检查失败，不能复制合成测试机床参数作为生产配置。

标准工艺CSV至少包含 `line,execution_instance,segment_mm,ap_mm,ae_mm,steady`；支持已有“序号 N ap ae F MRR s S G”文本导出。程序行号必须采用已核实映射；接触与工艺插值需要每执行段有充分位置支撑。按实验资料《CSV读取规则》第11节，Scope位置对齐优先使用完整实际XYZ；缺失时使用采集的完整指令XYZ，并记录 `position_source=command`。两种来源均需通过行号、统一坐标偏移、几何、执行实例和连续性检查，不混用XYZ来源；已有实际XYZ中的局部无效点不切换成指令位置补齐。实际进给优先直接实际进给通道，再用实际XYZ速度模，只有显式通过差分审核才使用实际XYZ位置差分；指令位置差分不能提供实际进给标签。负载还需主轴实测功率与转速。

正式NC网格间距0.5 mm。无接触、G0、暂停、缺失、无效区间和执行变化切断监督窗口。主趋势只用有效稳态和稳定转速点，残差可用全部有效切削动态。标签来源、窗口与掩码由服务生成，不能自行把无效点补成有效训练标签。

#### 单条补采：先审核，再切换有效版本

只缺一个有效程序位置时，不要求重做全轮五类。Python接口 `activate_record_replacement(records, replacement, base_dir=...)` 在内存中审核并返回新记录列表，不写文件、不改原输入、不启动训练。新记录必须显式指向一个当前有效的旧ID，保持相同轮次、类别、程序族和预定NC内容；`program_slot` 必须按协议明确填写。它将新记录与同轮其余四类合并检查，并与包括已替代记录在内的历史采样内容排重。任何必要检查失败均抛出 `ValueError`，原清单保持不变。

新记录须独立填写3.1节要求的文件、条件和审核事实，不能直接复制旧记录后只改文件名。以下只展示补采特有字段，**不是可直接运行的完整记录**；R74台阶T2尚待实际补采，示例不代表已采集或已替换：

```json
{
  "record_id": "REPLACE_新补采唯一ID",
  "replaces": ["REPLACE_R74台阶当前有效ID"],
  "round_id": 74,
  "feature": "台阶",
  "program_slot": "T2",
  "acquired_at": "REPLACE_ISO格式的实际采集日期或时间",
  "actual_event_order": null,
  "tool_session": null,
  "recollection": {
    "reason": "R74台阶按预定T2程序补采",
    "evidence_path": "REPLACE_真实补采记录或采集日志文件"
  }
}
```

`evidence_path` 相对 `base_dir` 解析，接口记录其SHA-256及新实测、预定NC哈希。新 `acquired_at` 必填；旧采集日期、刀具会话和顺序不得继承。新顺序已核实才填写，且必须晚于历史已知事件序号；否则保留 `null`，不得用74充当实际顺序。刀具会话未知也保留 `null`。接口不会将 `memory_eligible` 改成 `true`；未知会话或顺序的补采记录明确保持 `false`，最终资格仍由全清单审核决定。

完成真实补采和逐项审核后，可在AFC环境中使用以下调用方式（不会自动执行）：

```python
import json
from pathlib import Path
from project.load_prediction.dataset_manifest import activate_record_replacement, inspect_manifest

manifest_path = Path("REPLACE_现有开发清单绝对路径")
replacement_path = Path("REPLACE_已审核新补采记录JSON绝对路径")
manifest = json.loads(manifest_path.read_text(encoding="utf-8"))
replacement = json.loads(replacement_path.read_text(encoding="utf-8"))
updated_records = activate_record_replacement(
    manifest["records"], replacement, base_dir=manifest_path.parent
)
updated_manifest = {**manifest, "records": updated_records}
review = inspect_manifest(updated_manifest, base_dir=manifest_path.parent)
# 独立保存新清单，不能覆盖旧清单；相对文件路径仍以原清单目录为基准。
output_path = manifest_path.with_name("REPLACE_新的清单文件名.json")
with output_path.open("x", encoding="utf-8") as stream:
    json.dump(updated_manifest, stream, ensure_ascii=False, indent=2)
print({key: review[key] for key in ("feed_eligible", "load_eligible", "memory_eligible")})
```

旧记录只新增/修改 `status="superseded"` 和 `superseded_by`；其原始文件、时间、质量事实均保留。新记录登记 `replaces` 和补采证据。R74仍整体属于原开发折，补采不能提前写入历史记忆；已有训练快照也不会随新清单改变。激活记录只解决资料版本管理，基础功率资格、正式训练和记忆评价须分别满足原有门槛。

### 3.2 `base_validation`：正式负载标签的证据对象

```json
{
  "version": "REPLACE_基础模型内部版本",
  "model_path": "REPLACE_基础模型JSON绝对路径",
  "model_sha256": "REPLACE_模型文件64位小写SHA256",
  "report_path": "REPLACE_正式标签验证报告绝对路径",
  "report_sha256": "REPLACE_报告文件64位小写SHA256",
  "mode": "measured_speed_labels",
  "validated": true,
  "applicable": true,
  "domain": {
    "machine_id": "REPLACE_实际机床ID",
    "power_channel": "spindle_power_w",
    "spindle_rpm_min": 6000,
    "spindle_rpm_max": 10000
  }
}
```

此对象只有在证据本身满足条件后才可采用。服务核验：模型自身为 `validated_in_sample_domain`；报告的 `model_sha256/model_version/mode/domain`与对象一致；报告为 `status="validated"`且 `eligible_for_load_training=true`。路径、文件哈希、机床和转速域都须一致。`base_model_path`还必须指向相同模型文件。空载候选目前不满足此门控。

计算文件哈希可用：

```powershell
(Get-FileHash -Algorithm SHA256 -LiteralPath 'REPLACE_实际文件').Hash.ToLowerInvariant()
```

文件SHA与 `measurement_content_sha256`含义不同：后者由Scope实际采样内容规范化生成，不要用普通文件SHA冒充。`program_version`也应从真实NC解析取得，不是手填版本字符串。可在已设置 `PYTHONPATH=src` 的AFC环境用 `parse_nc(nc, MachineConfig.load(machine))["program_version"]`读取。

## 4. 检查和冻结准备结果

最小开发清单检查请求：

```json
{"manifest":"REPLACE_实际清单JSON绝对路径"}
```

返回重点是 `feed_eligible`、`load_eligible`、`blockers`、`missing_slots`、`missing_rounds`；`blockers[].scope`区分进给、负载、共同或保留资料。只训练进给不要求基础功率凭据，但仍要求完整开发协议、真实进给监督、接触和审核。不要因网页没有红字就推断资格通过。

`prepare`请求的JSON Schema摘要：

```json
{
  "$schema":"https://json-schema.org/draft/2020-12/schema",
  "type":"object",
  "required":["manifest","base_model_path","base_validation"],
  "properties":{
    "manifest":{"oneOf":[{"type":"string","minLength":1},{"type":"object","required":["records"]}]},
    "base_model_path":{"type":"string","minLength":1},
    "base_validation":{"type":"object","required":["version","model_path","model_sha256","report_path","report_sha256","mode","domain","validated","applicable"],"properties":{"mode":{"const":"measured_speed_labels"},"validated":{"const":true},"applicable":{"const":true},"model_sha256":{"type":"string","pattern":"^[0-9a-f]{64}$"},"report_sha256":{"type":"string","pattern":"^[0-9a-f]{64}$"}}},
    "dataset_role":{"enum":["development","memory_validation","target_adaptation","adaptation_validation","interval_calibration","independent_test"],"default":"development"}
  },
  "additionalProperties":false
}
```

可复制的构造方式，`base_evidence.json`应为上一节实际审核证据对象：

```powershell
$prepare = @{
    manifest = 'REPLACE_实际清单JSON绝对路径'
    base_model_path = 'REPLACE_已验证基础模型JSON绝对路径'
    base_validation = (Get-Content -Raw -Encoding utf8 -LiteralPath 'REPLACE_base_evidence.json' | ConvertFrom-Json)
    dataset_role = 'development'
}
$prepared = Invoke-RestMethod -Method Post -Uri "$api/prepare" -ContentType 'application/json; charset=utf-8' -Body ($prepare | ConvertTo-Json -Depth 64)
$prepared
```

准备目标工况、独立适配验证或最终测试时，分别设置 `dataset_role`为 `target_adaptation`、`adaptation_validation`、`independent_test`，并使用相应用途的清单。非开发用途不要求凑齐R01—R90或450位置；所选用途自身的来源、质量和基础标签凭据仍须通过。记录保留 `round_id/combination/parameter_group/feature`等样本与记忆上下文，但不得将目标记录伪装为开发轮次。不同用途分别获得独立快照ID。

```json
{
  "record_id":"target-A-fit-001",
  "dataset_role":"target_adaptation",
  "round_id":1,
  "combination":"target-A",
  "parameter_group":"target-A-setting-1",
  "feature":"外形",
  "program_id":"target-A-fit-program",

```

仅准备进给时请求为 `{"manifest":"REPLACE_开发清单路径"}`，发送至 `/prepare-feed`。该入口只准备开发进给快照，随后训练请求使用 `mode="feed"`。

## 5. 九折开发、全量冻结训练和任务状态

开发集为90轮×5类程序，九折按固定组合留出10轮；精确映射可查询 `/protocol`。P0为1—45轮，P1—P5为后续每组9轮。每折先训练/冻结进给，再训练/冻结物理主趋势，再构造残差标签并训练/冻结残差。正式端到端验证使用预测实际进给；实测进给只用于负载标签训练和明确诊断。

训练请求字段：

| 字段 | 类型/默认 | 含义 |
|---|---|---|
| `snapshot_id` | 必填string | 已准备的开发快照 |
| `mode` | `all`或`feed`，默认`all` | 联合三阶段或独立进给 |
| `candidates` | 可选object[] | 每项需唯一`id`，含下述配置对象 |
| `candidates[].feed_model` | object | `hidden_size,num_layers,dropout,window_points,context_points` |
| `candidates[].feed_training` | object | `epochs,learning_rate,batch_size,patience,min_delta,gradient_clip,seed` |
| `candidates[].load_model` | object | `coefficient_widths,hidden,dilations,kernel_size,attention_heads,attention_layers,window_points`等 |
| `candidates[].load_training` | object | `main_epochs,residual_epochs,learning_rate,main_batch_points,patience,min_delta,gradient_clip,seed` |

最小请求直接使用实现默认配置：

```json
{
  "snapshot_id":"REPLACE_准备返回的64位snapshot_id",
  "mode":"all",
  "candidates":[{"id":"default"}]
}
```

预览使用相同字段发送至 `/preview`；预览不训练。正式创建任务示例：

```powershell
$train = @{ snapshot_id = $prepared.snapshot_id; mode = 'all'; candidates = @(@{id='default'}) }
$preview = Invoke-RestMethod -Method Post -Uri "$api/preview" -ContentType 'application/json; charset=utf-8' -Body ($train | ConvertTo-Json -Depth 64)
$job = Invoke-RestMethod -Method Post -Uri "$api/jobs" -ContentType 'application/json; charset=utf-8' -Body ($train | ConvertTo-Json -Depth 64)
Invoke-RestMethod -Uri "$api/jobs/$($job.job_id)"
```

取消时发送非空JSON：

```powershell
Invoke-RestMethod -Method Post -Uri "$api/jobs/$($job.job_id)/cancel" -ContentType 'application/json' -Body '{}'
```

任务状态为 `queued → running → succeeded/failed/cancelled/interrupted`。单个输出目录串行执行；状态、进度及日志保存在 `jobs/<job_id>/`。`succeeded`表示后台调用完成，对论文对照还须读取 `result.status`及 `result.result.status`：等待资料的业务结果不代表完成科学实验。

按九折结果选定配置后，三个网络重新初始化，以全部开发资料训练；各阶段epoch取折内最佳epoch中位数向上取整。完整冻结文件先在暂存目录检查再发布到 `models/<model_id>`；失败或取消不覆盖旧正式模型。合成模型只进入 `synthetic_models`，默认 `/models`不返回它们。

正式 `all`任务要求三分位、物理描述输入、显式条件倍率；点回归、编号或隐式结构应通过独立论文对照入口。工况分支只有实际训练水平变化才可学习，固定工况90轮不能证明跨材料或跨机床收益。

## 6. 论文对照与七种新增适配入口

当前21个注册项均有对应服务路径。注册与实现可用不等于数据条件满足；`awaiting_multicondition_data`、`awaiting_data`和具体适配等待状态会原样保留。

| 对照ID | 执行内容 |
|---|---|
| `fixed_physical`、`local_physical` | 固定正系数或局部变系数物理基线，评分不叠加残差/记忆 |
| `no_condition`、`descriptor_condition`、`explicit_multipliers` | 关闭工况、物理描述、显式剪切/刃口倍率 |
| `id_condition` | 只读取显式字符串`condition_id`的诊断one-hot；未知编号严格拒绝；单水平冻结 |
| `implicit_condition` | 物理描述直接接入局部系数网络；返回显式倍率严格为1 |
| `no_residual_modulation`、`residual_modulation` | 关闭或启用残差条件幅值/偏置 |
| `no_memory`、`memory` | 冷启动记忆对照；评分后按实际事件顺序更新 |
| `point_output`、`quantile_output` | 有符号点回归MSE或有序三分位pinball；点回归没有统计区间 |
| `programmed_feed`、`measured_feed`、`predicted_feed` | 同一冻结负载模型比较编程/实测/预测进给，不更新记忆 |
| `zero_shot` | 源模型冻结，不使用目标拟合记录 |
| `four_parameter_calibration` | 共享网络冻结，只拟合剪切、刃口、残差倍率及残差偏置 |
| `physical_refit` | 只重新拟合物理系数相关参数，残差冻结并随新主趋势重算路径输入 |
| `output_finetune` | 仅指定输出头微调，主体网络冻结 |
| `full_retrain` | 源资料加目标适配资料重初始化负载网络；给定BiLSTM仍冻结，是非等预算参考 |

输出保存 `prediction.csv`和 `prediction.json`，并返回 `prediction_id,directory,columns`。主要列单位为W，位置单位为mm：

| 字段 | 含义 |
|---|---|
| `main_w`、`shear_w`、`edge_w` | 主趋势及剪切/刃口分量 |
| `residual_w`、`memory_w` | 有符号路径残差中位数、确定性同位置记忆 |
| `cutting_power_w`、`q50_w` | 切削功率中位数，两者一致 |
| `q05_w`、`q95_w` | 模型原始切削分位边界；包含已应用的主趋势、工况校准和记忆，但不含独立区间后处理扩展 |
| `lower_w`、`upper_w` | 当前有效预测区间；未校准时等于q05/q95；独立区间校准后为扩展后的界限 |
| `calibrated_lower_w`、`calibrated_upper_w` | 独立区间校准存在时，明确保存其边界 |
| `interval_status` | `model_prediction_interval`、`independently_calibrated_prediction_interval`或点对照的`point_regression_no_interval` |

展示风险、计算覆盖率及加工后评分应使用 `lower_w/upper_w`。保留 `q05/q95`是为了追溯未经区间后处理的模型输出，不能在已加载区间校准后仍用它们显示有效边界。点回归对照的上下列可以相等，但没有统计区间意义。

`model_id`是注册表ID；`model_version`是模型配置、权重、归一化及来源的内容版本；`prediction_version`由负载模型内容版本、工况校准版本和记忆策略共同确定。无工况校准/记忆时可与模型版本相等，有后处理时不可用裸模型版本替代。记忆策略包括schema、网格、更新率、最小重复数和一致性阈值，具体记忆状态文件另外由预测记录的 `memory_version`文件SHA追溯。独立区间校准版本也单独保存，不应混同为模型版本。

调用区间校准时，应直接使用保存的 `prediction.json.prediction_version`，并保持相同工况校准与记忆策略；不要自行拼版本字符串。更换低维校准或记忆策略后，旧区间校准将被拒绝。名义q05—q95为90%模型预测区间，实际覆盖需测量；不是95%置信区间。

### 8.1 工况四参数校准

请求显式填写 `kind="condition"`。底层保留省略时采用condition的兼容行为，但本文schema与示例统一要求明确填写，避免混淆两种校准。至少两份独立目标适配记录，以及未参与拟合的独立 `adaptation_validation`记录。拟合资料要求有效稳态/切削掩码和实测实际进给，且只能针对一个固定物理目标工况。它检查剪切/刃口及残差幅值/偏置设计矩阵的秩与条件数，不足时返回 `not_identifiable`或`rejected`，不会生成假校准。

每个拟合/验证记录的JSON Schema：

```json
{
  "$schema":"https://json-schema.org/draft/2020-12/schema",
  "type":"object",
  "required":["prepared_csv","prepared_csv_sha256","metadata"],
  "properties":{
    "prepared_csv":{"type":"string","minLength":1},
    "prepared_csv_sha256":{"type":"string","pattern":"^[0-9a-f]{64}$"},
    "metadata":{"type":"object","required":["record_id","dataset_role","measurement_content_sha256","resolved_files","file_sha256"],"properties":{"resolved_files":{"type":"object","required":["measurement"]},"file_sha256":{"type":"object","required":["measurement"]}}}
  }
}
```

服务同时检查准备CSV文件SHA、实测数值指纹、`metadata.resolved_files.measurement`原始文件SHA和采样内容SHA。拟合、验证和历史训练任意一组复用记录ID、原始实测内容或准备数值内容都会被拒绝；重新命名文件不能形成独立验证。

建议直接从准备快照取元数据，避免手抄错哈希。以下代码只读取现有快照并构造请求；若启动时使用了 `--output-dir`，必须把 `$serviceRoot`同步改为该目录：

```powershell
$serviceRoot = Join-Path (Get-Location) 'data/paper1/service'
function Get-PreparedLoadRecord([string]$snapshotId, [string]$recordId) {
    $dir = Join-Path $serviceRoot "snapshots/$snapshotId"
    $manifest = Get-Content -Raw -Encoding utf8 -LiteralPath (Join-Path $dir 'snapshot.json') | ConvertFrom-Json
    $items = @($manifest.records | Where-Object { $_.kind -eq 'load' -and $_.metadata.record_id -eq $recordId })

}

Invoke-RestMethod -Method Post -Uri "$api/calibrate" -ContentType 'application/json; charset=utf-8' -Body ($calibrate | ConvertTo-Json -Depth 64)
```

### 8.2 独立完整记录区间校准

请求 `kind="interval"`。默认alpha=0.1，有限分组校准至少需要9份完整独立拟合记录，另需非空外部验证；这些记录不能来自网络开发或最终测试。拟合记录的 `dataset_role="interval_calibration"`，外部验证为 `adaptation_validation`。

每个区间记录的JSON Schema：

```json
{
  "$schema":"https://json-schema.org/draft/2020-12/schema",
  "type":"object",
  "required":["group_id","dataset_role","prediction_version","prediction_directory","aligned_measurement","aligned_measurement_sha256","target_w","lower_w","median_w","upper_w","metadata"],
  "properties":{
    "group_id":{"type":"string","minLength":1},
    "dataset_role":{"enum":["interval_calibration","adaptation_validation"]},
    "prediction_version":{"type":"string","minLength":1},
    "prediction_directory":{"type":"string","minLength":1},
    "aligned_measurement":{"type":"string","minLength":1},
    "aligned_measurement_sha256":{"type":"string","pattern":"^[0-9a-f]{64}$"},
    "target_w":{"type":"array","minItems":1,"items":{"type":"number"}},
    "lower_w":{"type":"array","minItems":1,"items":{"type":"number"}},
    "median_w":{"type":"array","minItems":1,"items":{"type":"number"}},
    "upper_w":{"type":"array","minItems":1,"items":{"type":"number"}},
    "metadata":{"type":"object","required":["resolved_files","file_sha256","measurement_content_sha256"]}
  }
}
```

这里请求中的 `lower_w/median_w/upper_w`必须分别等于保存预测CSV的原始 `q05_w/q50_w/q95_w`。这是**拟合新校准器的输入定义**；与第7节应用已有校准器后对外使用有效 `lower_w/upper_w`的要求不同。不能把已扩展边界再用于拟合以重复扩展。

`prediction_directory`绑定原加工前预测目录；服务核验 `prediction.json`登记的CSV SHA、预测版本及三条原始分位数组。`aligned_measurement_sha256`绑定加工后实测CSV，`target_w`必须逐值等于其 `power_cut_w`；同时核验原始实测文件和采样内容。各数组等长、有限、按同一位置顺序排列；对齐键为 `line/execution_instance/segment_mm`。保留正确行序是资料制作者的责任，不要仅凭长度相同直接拼接两份文件。

`aligned_measurement`不是原始Scope文件。先将该次已完成实测按正确用途运行 `/prepare`：服务以程序行号及按读取契约选取的位置来源对齐NC网格，优先实际XYZ、缺失时使用采集指令XYZ，并记录 `position_source`；使用通过 `measured_speed_labels`验证的基础模型生成 `power_cut_w = 实测主轴功率 − 基础功率`。再从对应负载准备CSV按保存预测的位置键提取数据。下列代码生成对齐文件和原始来源元数据，且不修改加工前预测：

```python
from pathlib import Path
import json
import numpy as np
import pandas as pd
from project.load_prediction.training_service import TrainingService

service = TrainingService("REPLACE_与启动一致的服务输出目录")
_, load_samples, _ = service.load_prepared("REPLACE_该用途准备快照ID")
matched = [s for s in load_samples if s.metadata["record_id"] == "REPLACE_实际记录ID"]
if len(matched) != 1:
    raise ValueError("负载记录不存在或不唯一")
sample = matched[0]
prediction_dir = Path("REPLACE_原加工前预测目录")
pred = pd.read_csv(prediction_dir / "prediction.csv")
keys = ["line", "execution_instance", "segment_mm"]
source_columns = keys + ["power_cut_w", "aligned"]
aligned = pred[keys].merge(sample.frame[source_columns], on=keys,
                          how="left", sort=False, validate="one_to_one")
if not aligned.aligned.eq(True).all() or not np.isfinite(aligned.power_cut_w).all():
    raise ValueError("该完整记录存在未核实位置，不能删点、补零后用于区间校准")
aligned_path = prediction_dir / "aligned_measurement.csv"
metadata_path = prediction_dir / "calibration_source_metadata.json"
if aligned_path.exists() or metadata_path.exists():
    raise FileExistsError("保留既有证据，请使用新输出文件名")
aligned.to_csv(aligned_path, index=False, encoding="utf-8")
metadata_path.write_text(json.dumps(sample.metadata, ensure_ascii=False, indent=2,
                                    allow_nan=False), encoding="utf-8")
```

这一操作以已经核验的准备结果为来源，不重新估计基础功率或自行插值。若对齐不完整，应回查实际来源和工艺映射，不能截短保存预测CSV来凑齐数组。此时服务没有自动补齐完整校准记录的入口，应继续保留为不合格资料。

完整外层请求如下，`records`与 `validation_records`应分别替换成按上述schema构造的实际对象列表：

```json
{
  "kind":"interval",
  "model_id":"REPLACE_正式冻结模型ID",
  "condition_calibration":"REPLACE_同一预测使用的condition.json路径",
  "memory":"REPLACE_同一预测策略使用的记忆JSON路径",
  "records":[],
  "validation_records":[]
}
```

上例空数组仅表示待装入实际独立记录，直接提交会被拒绝；无工况校准或无记忆时删除对应字段。为避免手填数组，可在AFC中由已保存文件构造一条区间记录：

## 9. 总功率的两种证据模式

默认只输出切削功率，`total_power_status="total_power_unavailable"`。要增加基础功率，预测请求除第7节字段外，必须提供 `base_model_path`和 `base_validation`。此处的mode是 `steady_precutting`或`commanded_dynamic`，不同于训练标签的 `measured_speed_labels`，三者不得互换。

证据对象仍包括 `version,model_path,model_sha256,report_path,report_sha256,validated,applicable,mode,domain`。预测domain增加 `machine_settings_version`，并要求 `machine_id`、`power_channel="spindle_power_w"`、转速上下限与当前上下文及真实输入一致；这些身份字段也要出现在原预测请求的 `metadata`中。报告须自身为validated，绑定相同模型版本/哈希、mode和domain。动态模型须为 `validated_in_sample_domain`；稳态模式也接受 `validated_steady_in_sample_domain`。

| mode | 追加的证据/输入 | 成功状态 |
|---|---|---|
| `steady_precutting` | 报告`eligible_for_steady_prediction=true`；`metadata.spindle_stable_before_cut=true`；当前预测位置的主轴转速恒定且在域内 | `steady_total_power_estimate` |
| `commanded_dynamic` | 报告`eligible_for_dynamic_prediction=true`；完整均匀时间轴与S指令表；严格位置时间映射；完整NC时序及初态已核验 | `commanded_dynamic_total_power_prediction` |

稳态模式请求在第7节模板中增加：

```json
{
  "base_model_path":"REPLACE_已验证基础模型JSON",
  "base_validation":{
    "version":"REPLACE_基础模型内部版本",
    "model_path":"REPLACE_同一基础模型JSON",
    "model_sha256":"REPLACE_模型SHA256",
    "report_path":"REPLACE_稳态预测验证报告JSON",
    "report_sha256":"REPLACE_报告SHA256",
    "mode":"steady_precutting",
    "validated":true,
    "applicable":true,
    "domain":{"machine_id":"REPLACE_机床ID","machine_settings_version":"REPLACE_设置版本","power_channel":"spindle_power_w","spindle_rpm_min":6000,"spindle_rpm_max":10000}
  }
}
```

同时在原 `metadata`中加入经核实的 `spindle_stable_before_cut=true`。这是对完整预测请求的增量字段，不能把这段单独发送到 `/predict`。

动态模式把 `mode`改为 `commanded_dynamic`、使用相应报告，并在预测请求顶层增加：

```json
{
  "command_timeline":"REPLACE_完整指令时间轴CSV",
  "command_timeline_sha256":"REPLACE_时间轴文件SHA256",
  "time_mapping":"REPLACE_预测位置到时间映射CSV",
  "time_mapping_sha256":"REPLACE_映射文件SHA256",
  "complete_nc_timeline_verified":true,
  "initial_state_verified":true,
  "initial_speed_rpm":0.0
}
```

指令表列为 `time_s,commands_rpm`，至少3点，时间轴必须有限、严格递增、均匀、完整并包含等待与主轴动作；映射表列为 `line,execution_instance,segment_mm,time_s`，须精确且唯一覆盖预测位置，不缺失、不逆序、不越时间域。映射时刻的S指令须与空间预测的 `spindle_rpm`一致，整条动态时间轴所有点必须通过模型有效性检查。

动态证据的转速域还须覆盖初始转速、全部指令及预测转速。上例 `initial_speed_rpm=0`只有在已验证domain与模型都包含0rpm时可用；不能沿用仅覆盖6000—10000rpm的稳态证据。`initial_state_verified=true`表示已核实模型要求的稳定初态。只有空间NC网格时不能凭行程除以编程进给伪造时序，也不能把观测速度响应起点当成真实S指令时刻。

通过后增加 `base_power_w,total_power_w,total_quantiles_w,total_q05_w,total_q50_w,total_q95_w,total_lower_w,total_upper_w`。原始总功率分位由相同基础预测平移切削分位，当前有效总功率区间优先平移 `calibrated_lower_w/calibrated_upper_w`，否则平移有效 `lower_w/upper_w`。还保存 `base_model_version,base_prediction_mode,total_power_provenance`；后者包括证据哈希/适用域，动态模式另含时间轴与映射哈希、初始转速及模型时序说明。

`total_uncertainty_scope="cutting_component_only_base_estimate_added"`明确表示没有自动加入基础模型不确定性，因此不能把切削区间校准结论直接扩展为总功率联合覆盖保证。证据缺失或不适用时保留切削预测，并在 `total_power_reason`解释不可用原因。

| 服务目录 | 内容 |
|---|---|
| `snapshots/<snapshot_id>/` | 准备CSV、来源、掩码/类型、冻结基础证据与snapshot.json |
| `jobs/<job_id>/` | request.json、state.json、events.jsonl、worker.log及取消标记 |

| `feed_models/`、`synthetic_feed_models/` | 独立进给训练产物 |
| `predictions/<prediction_id>/` | prediction.csv/json、evaluation.json及更新后的记忆 |
| `calibrations/<id>/` | condition.json或interval.json以及report.json |
| `experiments/<id>/` | 独立对照的适配权重与审计报告，不自动进入正式模型表 |

| 现象 | 处理依据 |
|---|---|
| `base_not_validated` / 缺正式基础标签凭据 | 保持阻塞，补对应模式的独立验证；可先进行合格的进给工作 |
| 缺轮次/程序位置 | 补齐实际记录，或经审核单记录/整轮替换；不能复制文件补数量 |
| `quality_unknown` / `contact_unknown` | 核对真实采集和工艺证据，未确认保持未知 |
| 快照被修改 | 原快照只读，重新准备并取得新ID |
| 任务服务锁冲突 | 通过现有网页/API创建任务，或使用另一个输出目录 |
| `awaiting_multicondition_data` | 完成真实跨工况设计与独立资料，不把90轮重复当新工况 |
| `awaiting_supported_target_descriptor` | 当前源编码未覆盖目标；按明确低维校准或重训练路径处理 |
| `not_identifiable` / `awaiting_identifiable_target_data` | 增加能区分剪切/刃口及残差尺度/偏置的独立适配记录，不能仅重复同一设计 |
| 区间版本或分位数组不一致 | 回到已保存预测，核对完整prediction_version、条件校准、记忆策略及原始分位 |
| 旧模型/记忆不兼容 | 按当前契约重训练或记忆冷启动，不静默迁移旧输入格式 |

建议日常顺序：核对用途与真实来源 → inspect → prepare → preview → 创建任务 → 检查业务结果与冻结文件 → 加工前保存预测 → 加工后对齐评分 → 合格情况下更新记忆。工况与区间校准保留各自独立拟合和验证资料，最终测试只在冻结规则下评价。

本手册遵循单一职责：请求构造、资格检查、任务执行和科学解释分开说明；复用统一服务避免网页/CLI重复训练逻辑。输出仅引用已存在报告，不承诺未完成的真实数据精度、跨工况收益或覆盖率。
